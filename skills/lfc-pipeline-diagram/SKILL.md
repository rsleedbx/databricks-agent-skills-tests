# Pipeline diagram

`scripts/pipeline-diagram.py` (prints its usage with no arguments) reads the ingestion pipeline, its gateway and its UC connection with the Databricks CLI and prints both diagrams. Python 3 standard library only.

```bash
scripts/pipeline-diagram.py --pipeline <ingestion pipeline id> [--profile <profile>]
scripts/pipeline-diagram.py --pipeline <id> --source-cloud azure --source-host "VM + Podman" \
  --primary <host>,<port> --secondary <host>,<port> --firewall NSG \
  --secret-store "Azure Key Vault" --secret-kind uc -o diagram.md
```

| From the workspace | From flags |
|---|---|
| Gateway (serverless or classic cluster) or integrated CDC (one pipeline: extract, staging, apply) | `--source-cloud aws\|azure\|gcp\|laptop`, `--source-host` |
| Staging volume `__databricks_ingestion_gateway_staging_data-<id>` and its schema | `--primary` / `--secondary`: both nodes, the connection's target marked |
| UC connection name, type and `host:port` (the password is dropped as soon as it is read) | `--firewall` |
| Destination tables (first few, then a count) and SCD type | `--secret-store`, `--secret-kind uc\|workspace\|inline` |
| The workspace's cloud, from its URL | `--hide-host` leaves host names and ports out |
| How changes leave the source (below) | `--capture cdc\|ct\|cdc+ct` for SQL Server before its first run |
| | `--source-facts <file>` from `vm-facts.sh`, or `--vm "<text>"`: the source VM (below) |
| | `--model tpcc\|mautic\|...`, `--model-tables`, `--model-scale`: the data model loading the source (below) |

## Source VM, container and object storage

`scripts/vm-facts.sh azure <resource-group> <vm> [--subscription S]` or `vm-facts.sh aws <instance-id> [--region R] [--aws-profile P]` prints one JSON line: VM type, vCPU, RAM and each disk (size, type, IOPS, MB/s) from the cloud CLI. With `--ssh <user@host> [--key <file>] [--container <name>]` it also reads the VM: JuiceFS mounts (object storage behind them: Azure Blob or Amazon S3) and the database container's CPU and memory limits, SQL Server's memory cap and the data directory's size and whether it is on JuiceFS. Pass the file with `--source-facts` (or `SRC_FACTS` to `show-diagram.sh`); the diagram adds a VM, a container and a JuiceFS line under the source.

On a slot VM (`lfc-source-cloud-vm`), `slot.sh facts <name>` prints the same JSON from inside the VM (instance metadata, `/proc`, `findmnt`, the container), so it needs no cloud login; `lfc db up --workspace` saves it as `~/.config/lfc/source-facts/<connection>.json`. Without `--source-facts`, the diagram looks for `$LFC_FACTS_DIR/<connection>.json` (default that folder) and takes the source cloud and host from it, so a pipeline on an `lfc db up` connection shows its VM with no flags. Tested on Azure; the AWS path is written from the EC2 API and not run yet.

## Data model above the source

`--model <name>` draws what loads the source above it, with its number of tables: a statschema model (`tpcb` 4, `tpcc` 9, `tpch` 8, `tpcdi` 18, `tpcds` 24, `tpce` 32 tables, generated by datagen), `mautic` (128 tables, the application's own install and traffic), or any other name (`--model-tables N` for its count). `--model-scale` adds e.g. `SF 1` or `3 copies`. Without the flag, a facts file's `"workload": {"model", "tables", "scale"}` is used; `show-diagram.sh` takes `SRC_MODEL`, `SRC_MODEL_TABLES`, `SRC_MODEL_SCALE`. The statschema counts are kept here (this skill doesn't read statschema's files); the repo's checks compare them with the schemas.

## Medallion layers and reverse ETL

[`scripts/medallion.py`](scripts/medallion.py) counts the layers after the landing tables; `pipeline-diagram.py` draws them in a medallion box under what the ingestion lands, which is layer 1 (the Lakeflow Connect destination tables, or the Zerobus bronze table). `--layer NAME=CATALOG.SCHEMA[,...]` adds each next layer in flow order (`:only=t1,t2` for part of a schema), and `--reverse-etl TARGET[:METHOD[:TABLES]]` the last box, out to a database. Each layer shows its tables in all, materialized (streaming tables, materialized views, Delta tables) or not (views), and how each is written:

| Written as | From |
|---|---|
| SCD 1 / SCD 2 | an AUTO CDC flow (`flow_type` `CHANGE` or `SNAPSHOT_CHANGE` in the pipeline's `flow_definition` events); SCD 2 when the table has `__START_AT` and `__END_AT`; a Lakeflow Connect destination by its SCD type |
| append-only | an `APPEND` flow, or `--written NAME=append` for a table outside a pipeline (Zerobus bronze) |
| recomputed (MV) | a materialized view |
| keyed MERGE/update | a `MERGE`, `UPDATE`, `REPLACE_USING` or `REPLACE_WHERE` flow |
| written outside a pipeline | a Delta table no pipeline owns, without SCD 2 columns or `--written` |

`medallion.py` also runs alone (`--save layers.json`, then `--layers-json` to draw saved counts offline). `show-diagram.sh` takes `LAYERS` (space-separated `NAME=CATALOG.SCHEMA`) and `REVERSE_ETL`.

## SaaS connectors

A SaaS pipeline is read like a database one; the source box is the connector's REST API and the host it calls: from the connection's options (`instance_url`, `domain`, `host`, ...; never a secret field), the report URL (Workday reports), or the connector's public API host (Google Ads, Meta Ads, Slack, ...). Change capture is the connector's API reads. With a load tool for the source, `--model` draws it on top as for a database (`--model jira-test-data-generator --model-scale "Small, 5000 issues"`); without one, there is no model box. The connection, pipeline, landing tables, medallion and reverse ETL are the same as for a database.

The connector's table count (incremental and full-refresh tables, or "objects discovered from the source" for connectors that list them at run time) comes from an optional file, `$LFC_SAAS_TABLES` (default `~/.config/lfc/saas-tables.json`): `{"connectors": {"<CONNECTION_TYPE>": {"tables": N, "incremental": N, "full": N, "inventory": "finite|runtime"}}}`. Without it the box has no count.

## Kafka

A pipeline on a `KAFKA` connection is drawn as the topic and its broker, then the connection, the pipeline as a Kafka
consumer (its `starting_offset`) and the table with its key and value formats. The broker is named from the bootstrap
host (Azure Event Hubs `*.servicebus.windows.net`, Confluent Cloud, Amazon MSK, else Kafka). What the API can't see
comes from flags: `--broker "Standard, 4-40 TU, 32 partitions"`, `--producer` and `--producer-host` for what writes the
topic, `--probe` for a reader timing the table (`show-diagram.sh`: `BROKER`, `PRODUCER`, `PRODUCER_HOST`, `PROBE`).
Before the pipeline exists, `--pipeline-json` with the spec `pipeline.sh` prints and `--connection-json` with
`{"name", "connection_type": "KAFKA", "options": {"bootstrap_servers", "sasl_mechanism", "user"}}` draw the plan,
marked planned.

## Zerobus instead of Lakeflow Connect

`--ingest zerobus --engine <mysql|postgresql|sqlserver|oracle|db2|informix|cockroachdb|mariadb> --bronze CATALOG.SCHEMA.TABLE[,...]` draws the same source half (model, VM, database, change capture) with Debezium Server (`--producer`) on the source host pushing to the Zerobus ingest endpoint (a service principal, OAuth) and the append-only bronze change log, which is layer 1 of the medallion. No pipeline is read; the layers after bronze come from `--layer` as above.

## Managed databases

A connection whose host is a managed service's names the service and its cloud in the source box, with no VM or container: Azure SQL Database (`*.database.windows.net`), Azure SQL Managed Instance (`<name>.<zone>.database.windows.net`, public endpoint `<name>.public.<zone>.database.windows.net`, port 3342), Azure Database for PostgreSQL or MySQL flexible server, Amazon RDS and Aurora, CockroachDB Cloud (cloud from the host's region), Lakebase. `--source-cloud` and `--source-host` override it.

## Change capture per source

| Source | Shown as | Where it comes from |
|---|---|---|
| SQL Server | CDC (change tables `cdc.<capture instance>_CT`, utility objects for schema changes), change tracking (`CHANGETABLE`), or both | The pipeline's event `Replication tables: <n> CT tables, <m> CDC tables` (gateway or integrated pipeline); before the first run, `--capture` |
| Oracle | LogMiner on redo and archived redo logs | Connection type |
| MySQL, MariaDB | binlog in ROW format | Connection type |
| PostgreSQL | logical replication: slot and publication (pgoutput) | The pipeline's `source_configurations` |
| Query-based | a SELECT per run on a cursor column | `connector_type` other than `CDC` |
| SaaS | the connector's API, one pipeline | Connection type not a database |

The capture step is drawn on the node the connection points at (the secondary, when `--secondary` is the target).

`--format text|mermaid|both` (default both). With `-o <file>.md` each diagram goes in a fenced block, ready for a report; the Mermaid renders on GitHub as is.

## After every create

`scripts/show-diagram.sh <ingestion pipeline id>` prints "Components created for pipeline <id>:" and the text diagram to stderr (stdout stays free for scripts that print the id), saves text + Mermaid to `$DIAGRAM_MD` when set, and never fails the caller. `DIAGRAM=0` skips it. The flags come from `SRC_CLOUD`, `SRC_HOST`, `SRC_PRIMARY`, `SRC_SECONDARY`, `SRC_FIREWALL`, `SECRET_STORE`, `SECRET_KIND`, `CAPTURE`, `SRC_FACTS`, `SRC_VM`.

Called right after the create in `lfc-schema-change-test` (`lib.sh` `pipelines_create`, which also saves `$W/diagram.md`; `sqlserver-add-column.sh`; `integrated-scd2-ct.sh`) `lfc-meta-ads` (`pipeline.sh`) and `lfc-kafka-freshness-test` (`pipeline.sh`). A new script that creates an ingestion pipeline calls it the same way.

Tests: `tests/test_pipeline_diagram.py` runs the script on saved JSON (placeholder names): a gateway pipeline on an availability group, an integrated one, and the capture line per source.
